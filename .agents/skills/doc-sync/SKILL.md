# Document Sync（機能追加・Plan時のドキュメント精査）

機能追加や仕様変更のたびにコードとドキュメントが乖離するのを防ぐため、変更影響を受けるドキュメントを判定・同期する手順。

## 1. 変更種別と精査対象マッピング

変更内容に応じて、以下の対応表から精査対象ドキュメントを特定する。

| 変更種別 | 精査対象ドキュメント | 点検観点 |
| :--- | :--- | :--- |
| **ユーザー向け機能・UI・CLIコマンドの追加/変更** | [`README.md`](../../../README.md) | 「主な機能」「データ関連スクリプト」「ディレクトリ構成」に不足や古い記述がないか |
| **ストーリーJSONスキーマ・`stories-index.json`・ビルド/検証仕様の変更** | [`docs/architecture/DATA_ARCHITECTURE.md`](../../../docs/architecture/DATA_ARCHITECTURE.md) | 4章・6章のJSON例、フィールド定義、検証アルゴリズムと一致しているか |
| **新規ストーリー追加ルール・執筆手順の変更** | [`.agents/skills/genshin-story-curator/SKILL.md`](../genshin-story-curator/SKILL.md) | キュレーション手順や任意/必須フィールドの案内が最新か |
| **リテンション施策（Phase 1〜5）の着手・仕様確定・完了** | [`docs/handoff/retention/`](../../../docs/handoff/retention/) 配下の該当仕様書 | 完了条件（`- [x]`）の更新、選択式だった未確定仕様の確定反映、[`docs/handoff/RETENTION_ROADMAP.md`](../../../docs/handoff/RETENTION_ROADMAP.md) との整合 |
| **主要モジュールの追加・スキル追加・参照ポインター変更** | [`AGENTS.md`](../../../AGENTS.md) | Context Pointers のファイル一覧・機能要約・参照先が最新か |
| **設計ドキュメント群の追加・構成変更** | [`docs/README.md`](../../../docs/README.md) | ドキュメント索引表に漏れがないか |

> [!NOTE]
> [`docs/handoff/HANDOFF.md`](../../../docs/handoff/HANDOFF.md) はプロトタイプ期からの引き継ぎ履歴文書のため、明示的な指示がない限り更新対象外とする。

## 2. モード別の実行手順

### A. `/plan` モード（実装計画作成時）
1. 計画対象のコード・スキーマ変更を上表に照合し、影響を受けるドキュメントを洗い出す。
2. 更新が必要なドキュメントを実装計画書（`implementation_plan.md`）の `Proposed Changes` に `[MODIFY]` として組み込む。
3. スコープ境界や方針確認が必要な場合は、`Open Questions` または `User Review Required` に更新方針を明記する。
4. 更新不要と判定した主要ドキュメントがある場合は、計画内で対象外とした根拠を1行添える。

### B. 機能追加・仕様変更の実装時
1. コード・スキーマ・ビルドスクリプトの実装とビルド検証（`npm run validate` / `npm run build`）を完了する。
2. 上表の各点検観点に照らし、実装差分と乖離したドキュメントを列挙する。
3. 計画時点で合意済みのドキュメントは実装と同時に同期し、計画外の更新候補が見つかった場合は対象ファイル・更新案をユーザーへ提示して更新要否を確認する。
4. ドキュメント更新後、リンク切れやスキーマ例との矛盾がないか目視確認し、必要に応じて `npm run validate` を再実行する。

---

## 3. 完了条件（Completion Criteria）
- **計画作成時**: 計画書内にドキュメント変更対象候補の精査結果（更新対象または不要判断）が明記されていること。
- **実装完了時**: 影響ドキュメントが同期済み（またはユーザーへ更新提案済み）であり、実装内容とドキュメント間に矛盾がないこと。
